## 可追溯基线口径

既有 v22-validation.json 的 baseline 记录：8184 个 PCAP 记录，入站 applications=2830，scene_frames=2752，actions=20421，position_actions=7101，zstd=17。坐标按包号、类别、实体字段、scale、raw、帧号、时间戳、XYZ 对照 CSV。

旧文档的“3733 条双向应用消息”本次没有找到同口径依据，已撤下；2830 为入站解码器统计，不拿它推断双向总数。原始验证文件含玩家资料，未纳入公开包。

## 姓名问题与采集修复

合包漏名来自一条 UDP 记录内的两条连续 3/6 消息；多结果拆包与完整顺序传输分片修复在该真实样本有证据。合包拆分 2 个记录共 4 段，重组 1 条完整传输消息。用户反馈是现场事实，打包者离线结果是另一类事实。

v2.1 以前曾随端口变化反复启停抓包，历史记录边界有数秒空窗；连续采集避免因该启停机制再制造空窗，但不能把未记录字节补回，也不保证所有系统抓包零丢失。

## 发布修订检查范围

release-r1 只修辅助工具、文档、清单与 ZIP，不改变九个原机运行文件；其原始哈希仍在 SOURCE_ORIGIN.json。检查入口包括 build_dist.py --check、publish_check.py 与可选 --archive。最终实测结果由包外修复记录保存，不将“提供命令”写成“已执行成功”。

这类检查只能证明特定本地文件状态和最小辅助工具安全行为，不能替代现场观察。三个 .NET 8 工程的标准 SDK 构建尚待电脑端验收；跨电脑/跨手机部署未独立实测。

## 未支持或未验证

- IPv4/IPv6 分片重组、缺片/乱序传输分片修复不支持；输出 0 错误仍不等于全部流量已还原。
- 不支持地图配准、朝向、敌我、最大 HP/百分比或网络外实体。
- 3/2005 当前观察目标不保证原登录账号；额外 HP 值字段语义本轮未重新核对 IL。
- 全机 UDP 缓存存在隐私风险；时间、数量和体积淘汰可能丢弃数据。
- 截短 PCAP/记录结构检查属于离线工具预检；不改变原后端，也不能证明采集端没有丢包。
- 用户反馈、函数返回、文件回读、构建通过都不能单独替代实际游戏表现。

按 REPRODUCE 使用自己的私人样本核对，不提交原始流量或日志。
